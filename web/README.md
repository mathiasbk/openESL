# Web page: label designer and flasher

A static page for GitHub Pages (or any web server) with an overview, three tools, a setup guide and the API documentation:

| Tab | What it does |
|---|---|
| **Overview** | What OpenESL is, how the parts fit together, and what hardware you need. The landing page. |
| **Design** | Draws and edits layout files (docs/protokoll.md part 3) for every tag model in `js/models.js`, in three columns. On the left the layouts of the file ("+ New" adds an empty one, or one from the template library with "From template…": a dialog, `js/tplpicker.js`, that lists the catalog in `templates/` by category with a search, draws each template on the current model with the renderer and its `_sample` text, shows its fields and what it uses, and adds it only when the file still compiles with it, under a unique name, with its icons and sample text; with a template's layout selected, changing the model offers that template's variant for the other model. The catalog is read from `templates/index.json` next to the page, else from GitHub Pages; the AP's own designer reads GitHub Pages and falls back to its example layouts. `templates.mjs` checks the catalog and writes it to `dist/templates/` during the build, and `js/catalog.js` has what the picker and the check share; the format: `wiki/labels/Label-templates.md`. The selected layout has copy and delete) and the elements of the one picked, the one in front at the top, dragged to change the order. In the middle the tag, with the tools over it (text, fixed text, box, line, icon, barcode, QR code) and a bar by the selected element for how it looks: font, alignment, colour, and under "More" vertical alignment, lines, smaller fonts if the text does not fit, placing against an edge or in the middle, stretching, turning a line, and the drawing order. Boxes can be dragged and resized on the preview and snap to the screen's edges and centre and to the other boxes (Alt turns it off). On the right the layout's name, its fields each with the sample text the preview shows (renamed, added and removed there), where the selected element is and what it shows, and the description. Undo and redo (Ctrl+Z, Ctrl+Shift+Z) and keyboard shortcuts for the selected box (arrows, Tab, Esc, Delete, Ctrl+D to duplicate, Ctrl+C and Ctrl+V to copy a box to another layout). The status bar under the tag shows how much of the AP's limits the layout uses (the fullest one; the list of lines of text, boxes, file bytes, JSON bytes, fields and text bytes opens from it), counted as the AP's compiler counts them (`js/limits.js`, checked against the compiler by `test/limits.test.mjs`). The limits are the AP's, set per AP board (`"limits"` in `ap/boards/<board>/board.json`): once Send to tag has connected, they are the ones that AP reports in `GET /api/layouts` (`renderer.setLimits`, `web_set_limit` in `wasm/web_api.c`), otherwise the default board's (the ESP32-C6, the smallest), and the list says which. The status bar also shows whether the AP accepts the file, the preview's options and the zoom (1× to 6× tag pixels, or fitted to the window). "Send to tag…" opens a dialog that connects to the bridge in `tools/esl-client` (`esl_client.py --serial /dev/ttyACM0 serve`) at the address the Dashboard tab uses, lists the AP's tags of the model, uploads the layout file when the AP does not have this version and sends the sample text, then asks the AP whether the tag shows it (`js/apclient.js`). The File menu saves the layout file for `PUT /api/layouts/{model}` and a label design (`esl-label`) for `tag/tools/label_design.py`, opens a file, shows the file as JSON, or puts the example back. Its styles are in `css/designer.css`, so the AP does not carry them. |
| **Flash tag** | A guide in steps like Flash AP (`js/tagwizard.js`, styles in `css/apwizard.css`): **1** the tag model from a photo of each tag (`img/`) and the firmware, **2** the D1 mini running atc1441's ZBS_Flasher over Web Serial (drawn by `js/appics.js`), **3** the tag in the jig with its parts (MAC, backup, write, verify) and a row per tag flashed, **4** a summary with the backups to export. The same steps and checks as `tools/flash-tui` (MAC, backup before erase, MAC to the info page, write, verify); the info page is never erased. A tag with no MAC left (an earlier build wiped 0xFC06) gets a field, shown only then, for the barcode on its label or its MAC, and is flashed again with it. The firmware comes from the page's release or from a file, and "Keep going" waits for the next tag in the jig after each one. Backups are kept in the browser (IndexedDB, kept between visits until the site's data is cleared) with the barcode printed on the tag's label (filled in from the stock flash 0xFC06–0xFC0B as 12 hex digits, see `tools/flash-tui`; it can be changed by hand), and can be exported as a ZIP (all images plus `backups.csv`) or as the CSV list alone. |
| **Flash AP** | A guide in steps (`js/apwizard.js`, styles in `css/apwizard.css`, which the AP does not pack). **1 Choose AP:** a card per AP setup from the boards in `info.json` (`ap_boards`, from `ap/boards/`), drawn by `js/appics.js` (one board, a board with a screen, an S3 with a C6 radio on a cable or over WiFi), and the C6 radio (plain or with screen) where the board takes either. **2 Flash:** each board in the setup, the C6 radio first (`radios` in `info.json`, from `ap/radio/boards/` and `ap/netradio/boards/`), then the main board (an S3 or C5 on its port marked USB), then for the cable the wiring. Written with esptool-js (`js/apflash.js`; Espressif's, loaded from unpkg with its version pinned): it checks that the chip is the one the step is for and reads the partition table on the board: a blank board is erased first, and an AP that runs OpenESL gets only the bootloader, partition table, otadata and app of the manifest (`build.py` splits the merged image), so the AP keeps its WiFi, token, tags, layout files and tag firmware; when NVS is not where the new table has it (OpenESL from before 0.3.0, other firmware) it stops and offers to erase. The C6 radio on a cable is always erased first; the radio over WiFi is treated as an AP (its NVS is where the AP has it). **3 WiFi and token:** on the same port when the browser gives it back after the reset (`portAgain()`; otherwise the user picks it): network, password, name and a random token with a copy button, with the setup network as the way out; an AP on a network already keeps it and its token unless the user changes them (no empty password is sent). For the radio over WiFi it then sends the C6 its network and, if typed, the S3's address (empty: mDNS) on the C6's USB console and reads its log until it is connected (`js/radioconsole.js`). **4 Done:** the AP's address, board and version, with its dashboard. The plan for each setup, the partition table check and the radio's log lines are in `js/apsteps.js` (`test/apsteps.test.mjs`). |
| **Dashboard** | The AP's state (firmware, uptime, why it last started, channel, poll interval, time, schedule, WiFi) and a table of every tag (last check-in, the next one expected from its poll interval, or how late it is, signal, battery, firmware, and what it is waiting for or what is wrong, from `GET /api/health`), refreshed every 10 s while the tab is in view. Once connected, the connection is one line (where, which AP it is: its board, from `board_name` in `GET /api/tags` or the chip of an older AP, its name on the network and its firmware, and how long ago the AP last answered; red when it stops answering, and the figures below go grey), then four figures (tags, need attention, busy or late, scheduled) that also filter the table, the tag table with the state first, the last six digits of the MAC in bold and relative times (the clock time on hover), and the Access point and Firmware cards folded, each with a one-line summary. On a phone each tag is one row with its details on a line under it. Ticking tags brings up a box with the count (and how many of them Find or a filter hides) next to the filters, and the form to send them text or firmware. Forget in that box removes the ticked tags from the AP (`DELETE /api/tags/{mac}`: content, settings and scheduled content), after asking twice; a broken tag stays gone, one that still polls comes back as a new tag. Over the AP's USB port (Web Serial, the same connection as "WiFi and API token over USB", `js/apport.js`) or over HTTP through the bridge in `tools/esl-client`; a page on https may not call an AP on the local network itself. The AP serves the same dashboard at `/dashboard` (`ap/main/webui.py` packs this tab, `css/style.css` and the dashboard's modules into the firmware; `js/apdash.js` starts it with `initDashboard({ sameOrigin: true })`), so over WiFi it needs no bridge. Keep the dashboard's modules free of imports outside that list in `webui.py`. The figures are worked out in `js/dashdata.js` (`test/dashdata.test.mjs`). The Firmware card sends new AP firmware (`POST /api/ota`) or tag firmware (`PUT /api/tag-firmware`, which the AP then sends to the tags over the radio) in parts (16 KB for the AP, 8 KB for a tag image), from the files published with the page (the `-ota.bin` files `build.py --firmware` copies) or a file of your own, shows the AP's app slots and how far the tags of each model are, and waits for the AP to come back after its update. Before AP firmware goes out it names the version in the image and the one the AP runs, and warns when it is the same or older, or made for another chip or board (`chip` and `display` in `GET /api/ota`); when the page has a newer release than the AP runs, an arrow-up button next to the AP's version sends the image that fits it (`js/fwupload.js`, `test/fwupload.test.mjs`). Each row of the tag table has a tick box (the header's ticks every tag the table shows); under the table a list picks what goes to the ticked tags with the built-in layout `text`: the AP's address and WiFi, the tag's own info, today's date, or your own four lines, with a preview drawn by the AP's own code (on the AP's own page the renderer is loaded from the published page) and a list of what each tag gets. The same list offers the tag firmware published with the page: the AP gets the image for the first ticked tag of a model that needs it and gives it to the others too, and the list says what each tag gets or why it gets nothing (already has it, no radio updates). A word in braces in your own lines is filled in for each tag: `{ap_ip}`, `{ap_name}`, `{wifi}`, `{ap_fw}`, `{channel}`, `{tags}` from the AP, `{mac}`, `{model}`, `{battery}`, `{rssi}`, `{fw}`, `{seen}` from the tag, and `{weekday}`, `{date}` (Norwegian) and `{time}`; buttons put them in. When the lines have the date, the next days go to the AP as scheduled content for midnight (at most 50 rows in one `PUT /api/tags`), after the AP's clock is checked and, if it has none, set from the computer (`js/sendtext.js`, `test/sendtext.test.mjs`; `esl_client.py text` and `date` do the same for one tag). A tag that takes firmware over the radio (`"ota"` in `GET /api/tags`) and runs older firmware than the page has for its model gets a small arrow-up button in its firmware column in the tag table (the tooltip names the version), which gives the page's image to the AP. Tried on the AP and a 1.54" tag on 2026-10-15. |
| **Set up** | "WiFi and API token over USB" sets the AP's network and API token from the browser over its USB port (Web Serial, `PUT /api/wifi` in the `@ESL` frames of `ap/main/serial_api.c`, `js/apserial.js`, a port of `SerialClient` in `tools/esl-client`), for when a phone cannot join the setup network; it shows the AP's scan list, fills in a random token (`newToken()`) for an AP that has none, and watches the AP join. (`js/wifisetup.js`, `initWifiSetup(prefix)`.) Right after flashing, step 3 of the Flash AP tab does the same over the same cable. Then how to get a flashed AP going and keep it running: the first start on the setup network (`openesl-XXXX`, the form at `/setup`), the API token (where it is set, the Bearer header, what needs no token, the lockout after wrong tokens, changing or losing it), WiFi, and the day-to-day calls (content, health and webhook, OTA, backup, the long-term test). Plain HTML; keep it in step with `ap/README.md`. |
| **API** | The AP's HTTP API, interactive: `api.html` shows `docs/openapi.yaml` with [Scalar](https://github.com/scalar/scalar) (loaded from jsdelivr, version pinned), in a frame in this tab. "Test Request" sends real requests through the bridge in `tools/esl-client` (`esl_client.py --serial /dev/ttyACM0 serve`), which passes them on to the AP over USB or WiFi; a web page cannot reach the AP itself. Edit the spec, not the page; `ap/test/openapi/check_openapi.py` checks it against the AP code. |

Web Serial needs Chrome or Edge on a computer, and a secure page (https, or http://localhost).

## The preview is the AP's own drawing

`wasm/web_api.c` is built to WebAssembly with Emscripten, once per tag model. It links the AP's layout compiler (`ap/components/esl_core/esl_layout_compile.c`) and the AP's drawing (`esl_render.c`, with the tag's fonts and barcodes), which makes the image the AP sends to a tag. So:

- the preview is pixel for pixel the image a tag of that model gets and shows (the test checks the WebAssembly build against the same code built natively, and `sim/` checks the AP's drawing);
- an error under the preview is the message the AP answers with (`422`) when the file is uploaded;
- the size and version shown are those of the binary file the tags download.

A layout has up to six text fields that the client sends with each update, e.g. `price` and `price_ex` for the price inc. and ex. VAT (the AP does not work out VAT). What the format can draw: text in a box (six fonts, alignment, up to 3 lines, black, white, inverted, highlighted), fixed texts that are part of the layout (such as "inkl. mva"), boxes in black or white (filled or only a border, with round corners if you like), straight and slanted lines 1 to 16 px wide, small pictures (icons, made from a PNG, JPEG or GIF with the Icon button: dark pixels are drawn, up to 128 px), one barcode per layout (Code 128 or EAN-13, from a field) and one QR code per layout (from a field, e.g. a link). A black area with white text is a black box with white text on it, or inverted text. The compiler still limits the number of boxes (inverted and highlighted text count as one each), lines, icons and lines of text per layout (`ESL_DRAW_MAX_RECTS`, `ESL_DRAW_MAX_LINES`, `ESL_DRAW_MAX_ICONS` and `ESL_DRAW_MAX_RUNS` in `shared/proto.h`, and more on AP boards with PSRAM: `ap/boards/README.md`); the status bar under the preview shows how much of each a layout uses on the connected AP.

## Build and test

```bash
source /path/to/emsdk/emsdk_env.sh      # Emscripten 3.1.74
python web/build.py                     # renderer + page into web/dist/
python web/build.py --native            # native build of web_api.c, for the test
node --test web/test/*.test.mjs
cd web/dist && python -m http.server    # http://localhost:8000
```

`js/zbs.js` and `js/tagflash.js` are ports of `tools/flash-tui/zbs_proto.py` and `workflow.py`; `test/tagflash.test.mjs` runs them against a simulated ZBS_Flasher (`test/fake_flasher.mjs`, a port of `fake_flasher.py`). `js/apserial.js` is a port of `SerialClient` in `tools/esl-client/esl_client.py`; `test/apserial.test.mjs` runs it against a fake AP with log lines in the stream. Keep the ports in step with the Python originals.

## Publishing

`.github/workflows/web.yml` builds the tag firmware (SDCC 4.5.0, every model) and the AP (ESP-IDF v5.5.5, every board, each merged into one image at offset 0) through `firmware.yml`, builds the page and the renderer, runs the tests, and publishes `web/dist` to GitHub Pages on every push to `master`. The firmware the flash tabs offer is the latest GitHub release (`firmware/info.json` says which); before the first release it is the firmware built from that commit. Pull requests build and test only, and attach the page, with the firmware built from the pull request, as an artifact. See "Releases" in the top-level README.

One-time setup in the repository: Settings → Pages → Source: **GitHub Actions**.

esptool-js is loaded from unpkg (`esptool-js@0.6.1`, in `js/apflash.js`); everything else is in this folder.
