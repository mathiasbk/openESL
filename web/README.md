# Web page: label designer and flasher

A static page for GitHub Pages (or any web server) with an overview, three tools, a setup guide and the API documentation:

| Tab | What it does |
|---|---|
| **Overview** | What OpenESL is, how the parts fit together, and what hardware you need. The landing page. |
| **Design** | Draws and edits layout files (docs/protokoll.md part 3) for the 2.9" and the 1.54". Boxes can be dragged and resized on the preview; text, inverted text, lines and filled boxes can be added. Undo and redo (Ctrl+Z, Ctrl+Shift+Z) and keyboard shortcuts for the selected box (arrows, Tab, Esc, Delete, Ctrl+D to duplicate). A list of the elements picks boxes that lie under others, and meters under the preview show how much of the tag's limits the layout uses (lines of text, boxes, file bytes, fields, text bytes), counted as the AP's compiler counts them (`js/limits.js`, checked against the compiler by `test/limits.test.mjs`). Dragged boxes snap to the screen's edges and centre and to the other boxes (Alt turns it off), and buttons put the selected box against an edge, in the middle, or stretch it. "Send to AP" uploads the layout file and sends the sample text to a tag through the bridge in `tools/esl-client` (`esl_client.py --serial /dev/ttyACM0 serve`), then asks the AP whether the tag shows it (`js/apclient.js`). Zoom shows the tag in tag pixels (1× to 6×) or fitted to the window. A selected box has handles on all corners and edges; Ctrl+C and Ctrl+V copy a box to another layout. "+ From template" adds a copy of a layout from the example file (`tag/designs/layouts/<model>.json`, e.g. the product labels `vare`, `vare-mva` and `vare-priser` with the price both ex. and inc. VAT), with the sample values in its `_sample` key. Saves the layout file for `PUT /api/layouts/{model}` and a label design (`esl-label`) for `tag/tools/label_design.py`. |
| **Flash tag** | Flashes tags through a D1 mini running atc1441's ZBS_Flasher, over Web Serial. The model is picked from a preview of each tag. The same steps and checks as `tools/flash-tui` (MAC, backup before erase, MAC to the info page, write, verify); the info page is never erased. A tag with no MAC left (an earlier build wiped 0xFC06) gets a field, shown only then, for the barcode on its label or its MAC, and is flashed again with it. The firmware comes from the page's release or from a file, and "Keep going" waits for the next tag in the jig after each one. Backups are kept in the browser (IndexedDB, kept between visits until the site's data is cleared) with the barcode printed on the tag's label (filled in from the stock flash 0xFC06–0xFC0B as 12 hex digits, see `tools/flash-tui`; it can be changed by hand), and can be exported as a ZIP (all images plus `backups.csv`) or as the CSV list alone. |
| **Flash AP** | Flashes the ESP32-C6 access point with esp-web-tools: the plain image, or, with the checkbox, the one with a status screen for C6 boards with a 0.96" LCD. Without "Erase device" only the bootloader, partition table, otadata and app are written (`build.py` splits the merged image), so an AP already running OpenESL keeps its WiFi, token, tags, layout files and tag firmware; with it the whole flash is erased first. |
| **Dashboard** | The AP's state (firmware, uptime, why it last started, channel, poll interval, time, schedule, WiFi) and a table of every tag (last check-in, the next one expected from its poll interval, or how late it is, signal, battery, firmware, and what it is waiting for or what is wrong, from `GET /api/health`), refreshed every 10 s while the tab is in view. Over the AP's USB port (Web Serial, the same connection as "WiFi and API token over USB", `js/apport.js`) or over HTTP through the bridge in `tools/esl-client`; a page on https may not call an AP on the local network itself. The AP serves the same dashboard at `/dashboard` (`ap/main/webui.py` packs this tab, `css/style.css` and the dashboard's modules into the firmware; `js/apdash.js` starts it with `initDashboard({ sameOrigin: true })`), so over WiFi it needs no bridge. Keep the dashboard's modules free of imports outside that list in `webui.py`. The figures are worked out in `js/dashdata.js` (`test/dashdata.test.mjs`). The Firmware card sends new AP firmware (`POST /api/ota`) or tag firmware (`PUT /api/tag-firmware`, which the AP then sends to the tags over the radio) in 16 KB parts, from the files published with the page (the `-ota.bin` files `build.py --firmware` copies) or a file of your own, shows the AP's app slots and how far the tags of each model are, and waits for the AP to come back after its update. Before AP firmware goes out it names the version in the image and the one the AP runs, and warns when it is the same or older, or made for the other board (with or without the status screen, `display` in `GET /api/ota`); when the page has a newer release than the AP runs, an arrow-up button next to the AP's version sends the image that fits it (`js/fwupload.js`, `test/fwupload.test.mjs`). Each row of the tag table has a tick box (the header's ticks every tag the table shows); under the table a list picks what goes to the ticked tags with the built-in layout `text`: the AP's address and WiFi, the tag's own info, today's date, or your own four lines, with a preview drawn by the tag's own code (on the AP's own page the renderer is loaded from the published page) and a list of what each tag gets. A word in braces in your own lines is filled in for each tag: `{ap_ip}`, `{ap_name}`, `{wifi}`, `{ap_fw}`, `{channel}`, `{tags}` from the AP, `{mac}`, `{model}`, `{battery}`, `{rssi}`, `{fw}`, `{seen}` from the tag, and `{weekday}`, `{date}` (Norwegian) and `{time}`; buttons put them in. When the lines have the date, the next days go to the AP as scheduled content for midnight (at most 50 rows in one `PUT /api/tags`), after the AP's clock is checked and, if it has none, set from the computer (`js/sendtext.js`, `test/sendtext.test.mjs`; `esl_client.py text` and `date` do the same for one tag). A tag that takes firmware over the radio (`"ota"` in `GET /api/tags`) and runs older firmware than the page has for its model gets a small arrow-up button in its firmware column in the tag table (the tooltip names the version), which gives the page's image to the AP. Tried on the AP and a 1.54" tag on 2026-10-15. |
| **Set up** | "WiFi and API token over USB" sets the AP's network and API token from the browser over its USB port (Web Serial, `PUT /api/wifi` in the `@ESL` frames of `ap/main/serial_api.c`, `js/apserial.js`, a port of `SerialClient` in `tools/esl-client`), for when a phone cannot join the setup network; it shows the AP's scan list, fills in a random token (`newToken()`) for an AP that has none, and watches the AP join. The same card (`js/wifisetup.js`, `initWifiSetup(prefix)`) is step 2 on the Flash AP tab, so a freshly flashed AP gets its WiFi and token over the same cable. Then how to get a flashed AP going and keep it running: the first start on the setup network (`openesl-XXXX`, the form at `/setup`), the API token (where it is set, the Bearer header, what needs no token, the lockout after wrong tokens, changing or losing it), WiFi, and the day-to-day calls (content, health and webhook, OTA, backup, the long-term test). Plain HTML; keep it in step with `ap/README.md`. |
| **API** | The AP's HTTP API, interactive: `api.html` shows `docs/openapi.yaml` with [Scalar](https://github.com/scalar/scalar) (loaded from jsdelivr, version pinned), in a frame in this tab. "Test Request" sends real requests through the bridge in `tools/esl-client` (`esl_client.py --serial /dev/ttyACM0 serve`), which passes them on to the AP over USB or WiFi; a web page cannot reach the AP itself. Edit the spec, not the page; `ap/test/openapi/check_openapi.py` checks it against the AP code. |

Web Serial needs Chrome or Edge on a computer, and a secure page (https, or http://localhost).

## The preview is the tag's own drawing

`wasm/web_api.c` is built to WebAssembly with Emscripten, once per tag model. It links the tag's drawing code (`tag/src/layout.c`, `draw.c`, the fonts), the tag's file check (`layout_file_install`) and the AP's layout compiler (`ap/components/esl_core/esl_layout_compile.c`), the same sources `tag/tools/render_host.py` uses for the previews. So:

- the preview is pixel for pixel what a tag of that model draws (the test checks this against the same code built natively);
- an error under the preview is the message the AP answers with (`422`) when the file is uploaded;
- the size and version shown are those of the binary file the tags download.

A layout has up to six text fields that the client sends with each update, e.g. `price` and `price_ex` for the price inc. and ex. VAT (the AP does not work out VAT). What the format can draw: text in a box (four fonts, alignment, up to 3 lines, black, white, inverted, highlighted), fixed texts that are part of the layout (such as "inkl. mva"), filled boxes in black or white, and one barcode per layout (Code 128 or EAN-13, from a field). A line is a box 1 or 2 px wide; a black area with white text is a black box with white text on it, or inverted text. The tag's scene has room for a limited number of boxes (inverted and highlighted text count as one each) and lines of text per layout (`ESL_DRAW_MAX_RECTS` and `ESL_DRAW_MAX_RUNS` in `shared/proto.h`); the meters under the preview show how much of each a layout uses. Diagonal lines and images are not in the format.

## Build and test

```bash
source /path/to/emsdk/emsdk_env.sh      # Emscripten 3.1.74
python web/build.py                     # renderer + page into web/dist/
python web/build.py --native            # native build of web_api.c, for the test
node --test web/test/*.test.mjs
cd web/dist && python -m http.server    # http://localhost:8000
```

`js/zbs.js` and `js/tagflash.js` are ports of `tools/flash-tui/zbs_proto.py` and `workflow.py`; `test/tagflash.test.mjs` runs them against a simulated ZBS_Flasher (`test/fake_flasher.mjs`, a port of `fake_flasher.py`). `js/apserial.js` is a port of `SerialClient` in `tools/esl-client/esl_client.py`; `test/apserial.test.mjs` runs it against a fake AP with log lines in the stream. Keep the ports in step with the Python originals.

## Publishing

`.github/workflows/web.yml` builds the tag firmware (SDCC 4.5.0, both models) and the AP (ESP-IDF v5.5.5, merged into one image at offset 0) through `firmware.yml`, builds the page and the renderer, runs the tests, and publishes `web/dist` to GitHub Pages on every push to `master`. The firmware the flash tabs offer is the latest GitHub release (`firmware/info.json` says which); before the first release it is the firmware built from that commit. Pull requests build and test only, and attach the page, with the firmware built from the pull request, as an artifact. See "Releases" in the top-level README.

One-time setup in the repository: Settings → Pages → Source: **GitHub Actions**.

esp-web-tools is loaded from unpkg (`esp-web-tools@10.4.0`); everything else is in this folder.
